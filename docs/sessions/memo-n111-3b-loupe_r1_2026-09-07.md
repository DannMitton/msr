## 3. Ruling 1. The loupe stays open, and the cause was the last fix's shadow

`apps/web/src/routes/+page.svelte:1382-1408`, one new guard inside
`handlePageTap`'s `loupeOpen` branch:

```js
if (gestureBeganOnSurface) return;
```

**The cause, measured rather than guessed.** N.111-3a made the loupe redraw in
the same frame as the placing click, and Dann confirmed on `d5a49ff` that the
redraw held. That fix is what closed the loupe:

1. A click inside the loupe places the syllable and `doc.pairings` changes.
2. The pane redraws, `onpagesdrawn` fires, `pageRevision` bumps.
3. The loupe's own effect rebuilds `frame`, and Svelte replaces the window's
   `{@html frame.inner}` (`Loupe.svelte:926`, `:939`).
4. The clicked element is now detached, **and it was removed with only the
   `{@html}` subtree**, so its ancestor chain stops short of `.loupe`. The
   existing target test, `e.target.closest('.loupe, .surface')`, answers null.
5. The geometry test below it then finds a `.score-page` box under the pointer,
   because on a desk the loupe stands over the page, and dismisses.

**Why it reads as a rule about placement and not about clicks.** A loupe click
with nothing armed mutates nothing, rebuilds nothing, and never closed. Only a
placing click destroys its own target.

**Why this guard and not a new one.** `gestureBeganOnSurface` is set at
`pointerdown`, when the DOM is still whole, and cleared on the frame *after*
`pointerup`, so it is standing when the click arrives. The branch below already
trusts it for exactly this reason, on the synthesized-click case. This adds one
reader; it invents nothing.

**Deliberately not fixed here:** Dann's observation 4 on the same walk, that a
second click on the same note seats the cursor's next syllable over the first.
That is the cursor's ruled advance working. What made it confusing was the
loupe closing, which is now gone, and what makes it recoverable is Undo, which
is now there.

## 4. Ruling 2. Undo and Redo, one stack extended

### 4.1 What the existing stack already covered, established first

`undoStack` (`+page.svelte:716`) is a **snapshot** stack, not a list of inverse
verbs. Each entry holds `{note, corrections, pairings, selected, gapAfter}` as
they stood **before** the verb, and `handleUndo` restores all of it. Nine verbs
push into it today, from both surfaces, through the same handlers:

| key | verb |
|---|---|
| `loupe.undo.deleted` | note removed |
| `loupe.undo.dotOn` / `dotDouble` / `dotOff` | the dot cell |
| `loupe.undo.restored` | corrections cleared |
| `loupe.undo.entered` | a note entered in a gap |
| `loupe.undo.rest` | note to rest and back |
| `loupe.undo.tie` | the tie |
| `loupe.undo.tuplet` | a tuplet defined |
| `loupe.undo.lyrics` | **syllables shifted**, the key Dann named |
| a `change` note | any pitch or duration change, read as `from → to` |

**`loupe.undo.lyrics` covers the shifts and nothing else.** It is pushed once,
in `handleDockShift` (`+page.svelte:1348` at the floor), for both scopes and
both directions. **Placement was never in the stack**, which is the gap Dann's
walk found.

### 4.2 What this paste adds

- **`pairingCursor` joins the snapshot.** A placement advances the queue, so an
  undo that restored only the pairing would leave the queue one syllable ahead
  and the next click would place the wrong word. Every other verb leaves the
  cursor alone, so carrying it costs those entries nothing.
- **`snapshot()` and `restore()`** are lifted out, so the two directions cannot
  disagree about what a state is.
- **`redoStack`**, the same entry type. `handleUndo` hands the state it is about
  to replace to it; `handleRedo` mirrors that. Neither knows what a verb does,
  which is the property that let one stack cover nine verbs.
- **`pushUndo` clears `redoStack`.** A new action drops the future, so the Redo
  pill can never offer a state that branched away.
- **`placeArmedSyllable` pushes**, after its early return, so a click with an
  empty queue leaves no pill that would undo nothing.
- **`redoLabel`**, composed at render by the same reader as `undoLabel`, so a
  singer who changes language mid-session reads both pills in the language they
  are now in.
- **The Redo pill** in `CorrectionSurface.svelte`, on the row the Undo pill
  already reserves. It keeps every one of that pill's rules: absent rather than
  disabled, named after the action, `flex: 0 1 auto` so a long sentence wraps
  inside the pill instead of pushing its neighbour. **One component, so the
  drawer's panel and the phone's dock cannot drift.**

## 6. Ruling 4. The CSS comment, verified, with a positive control

### 6.1 On the production build, the rendered result

Both rules are in the served stylesheet, scoped:

```
.char-warning.svelte-c9amm4 { font-size: 0.7rem; color: rgb(217, 119, 6); font-family: var(--font-sans); }
.error-text.svelte-c9amm4   { font-size: 0.75rem; color: rgb(217, 119, 6); font-family: var(--font-sans); }
```

`.char-warning` was then **provoked for real**, not inspected: 5,500 characters
typed into the intake raised `5,500 characters. Large texts may be slow to
process.`, and the live element computed to

- `color: rgb(217, 119, 6)`
- `font-size: 11.2px` (0.7rem)
- `font-family: "Source Sans 3", system-ui, …`

class `char-warning svelte-c9amm4`.

### 6.2 The control, because a positive result needs one too

`.error-text` fires on a transcribe error, which this walk could not provoke, and
a rule you can find in a stylesheet proves nothing until you know the instrument
can also fail. So both stylesheets were compiled and **parsed by the browser**:
the component as it stands, and the same component with that one ` */` stripped
back out.

| stylesheet | `.char-warning` | `.error-text` |
|---|---|---|
| fixed | `rgb(217, 119, 6)`, 11.2px | `rgb(217, 119, 6)`, 12px |
| the `*/` removed | `rgb(0, 0, 0)`, 16px | `rgb(0, 0, 0)`, 16px |

**And the mechanism, which is worth writing down.** The Svelte compiler does not
fail on the unterminated comment. It **recovers, emits both rules, and passes the
dangling `/*` through into the stylesheet verbatim**, so the compiled CSS reads:

```
	/* THE OCR CAMERA BUTTON'S RULES ARE GONE, …
	   … so it has a second reader.

	.char-warning {
```

The browser's CSS parser then swallows everything from that `/*` onward. **The
tell that the compiler knew something was wrong is the scope hash: in the broken
build the two selectors come out bare, `.char-warning`, where every other rule in
the file carries `.svelte-…`.** A `svelte-check` pass and all five gates are
blind to this, which is how it stood since early September.

## 9. The instrument, and one thing this session should have looked up first

**Both of the traps this walk hit were already in `ENVIRONMENT.md`, and it cost
about half an hour to rediscover them.** Recorded plainly rather than tidied,
because tether 16 is the one that was broken: search the project before forming
an opinion, including about your own tools.

1. **`vite preview` builds its file table at boot.** A fixture staged after the
   server is up 404s in `build/`, in `.svelte-kit/output/client/` and in
   `static/` alike, and the same file was moved through all three before a
   restart fixed it in one go. Already at `VITE PREVIEW BUILDS ITS FILE TABLE AT
   BOOT` (2026-09-03) and `WHAT VITE PREVIEW ACTUALLY SERVES` (2026-09-07).
   **One sentence is genuinely new and has been added there:** from inside the
   page the 404 does not look like one, because SvelteKit answers it with the
   fallback document, so `fetch(...).text()` returns about 2 kB of the app's own
   HTML and only `response.status` says it missed.
2. **The dictionary stayed at `Loading dictionary…`, disabled, all session.** No
   shard request, no console error, no service worker. This is **not** an
   unexplained hang: it is `A HIDDEN TAB` and `THE WALKCLOCK HARNESS`, both
   already written down. The Browser pane is a hidden tab, Chrome clamps
   `setTimeout`, and the loader's `setTimeout(0)` yield every 1500 entries never
   comes back, so the second shard is never fetched.
   **The walkclock harness was not used here, and did not need to be:** loading
   a lyric-bearing score fills `slotQueue` from the score's own words
   (`scoreTextQueue`, `+page.svelte:346`) whenever the singer's transcription is
   empty, so `placeArmedSyllable`, `SyllableStation` and both shifts all work
   with the dictionary still loading. That is the cheaper route for any walk of
   the pairing layer, and it is worth knowing beside the harness.
